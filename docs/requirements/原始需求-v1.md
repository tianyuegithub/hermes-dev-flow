## 一、核心闭环（4 步）

### Step 1 · 需求提交与评审
- 用户告诉 Hermes："我在 XX 项目空间下有一个需求"
- Hermes **自动调用「多模型融合评估」skill（MY）** 对需求做评审
- 评审对象：用户提出的需求本身

### Step 2 · 需求拆分
- 评审完成后，拆 **spec（需求）→ 设计 → 契约（合同）**
- 最终必须**让人确认**（人工确认是硬环节，不可跳过）

### Step 3 · 任务分发
- 确认完毕后，Hermes 根据：
  - 项目情况
  - K3s 里跑着的 worker（codex / claude code / opencode）
- **自动分发给 worker**

### Step 4 · DAG 拆解与调度
- 拆分时可能拆成多个任务，最终形成一个 **DAG 图（workflow 样式）**
- **每个节点由一个 worker 负责**
- 所有节点的**输入和产出都是这个 spec**
- **Hermes 统一调度**，最终完成工作

## 二、基础设施（7 条）

### 2.1 Git 版本管理
- 全程 Git 管理（分支、提交、release、PR）

### 2.2 Worker 热池（slot 槽位制）
- 在 **K3s** 里为**每个项目**预制一些 Pod（类似 slot 槽位）
- 选择 worker 时**复用**这些预制 Pod

### 2.3 关系与调度
- **项目 ↔ worker = 1 对多**
- **worker ↔ 任务 = 1 对 1**
- worker 完成当前任务并**提交 release 后**，可再接**当前项目**的其他任务
- 全部由 **Hermes engine** 分配

### 2.4 Pod 镜像
- 镜像包含各种开发框架：**Codex、Claude Code、OpenCode** 等
- 内部模型可以不同，或统一都用 Claude Code
- 模型：**DeepSeek、GLM、Kimi K3、千问** 等
- 模型跑在 **K3s 的 Pod 里**（不是本地 Mac）

### 2.5 启动与配置
- 初始化启动时：**指定并注入 Base URL 和 API Key**
- **Base URL / API Key 由 K3s 统一管理**，仅在 Pod 启动时注入
- 每个 Pod 启动时**拉取对应项目的分支**进行初始化

### 2.6 优化加速
- 使用**缓存**
- **共用 Node 和 Maven 环境**（Node.js 环境尝试共用）

### 2.7 监控与通知
- 整个过程**在 Hermes 里通过命令实时查看**
- **Hook 通知机制**：在 Hermes 主线程里实时看到进展

## 三、角色关系图

```
项目空间 A ──┬── worker-1 (Claude Code)  ←── 任务 a1 (1对1)
             │                              └→ release → 再接任务 a2
             ├── worker-2 (Codex)       ←── 任务 a3
             └── worker-3 (OpenCode)    ←── 任务 a4
                                          (DAG: a1→a3, a1→a4, a4→a2)
                                              ↑ Hermes engine 调度
                                              ↑ 所有节点输入/产出 = spec
```
