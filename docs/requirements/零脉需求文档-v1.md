> **作者**: 田悦 / Hermes

## 一、项目定位

**一句话**: 把 AI 编码能力从"个人工具"升级为"平台化研发产能"——用户说需求，Hermes 编排多智能体自动完成开发全流程。

**要解决的问题**:
- 批量重复性工作（跨仓库补丁、依赖升级、文档补全）消耗人力
- 交付周期受限于人头，大任务只能串行排队
- AI 编码能力强但停留在个人使用，缺乏统一调度和质量治理

**核心承诺**:
- 需求 → 评审 → 拆解 → 分发 → 执行 → 闸门 → 交付，全链路自动化
- 每个节点输入/产出都是 spec，Hermes 统一调度
- 质量不靠信任，靠契约 + 自动评分 + 人工闸门

## 二、总体架构

```
用户（自然语言 / Hermes 对话）
    │
    ▼
① 需求提交 ──→ 多模型融合评审（my-fusion skill）
    │
    ▼
② 需求拆分：spec → 设计 → 契约 ──→ 人工确认（硬闸门）
    │
    ▼
③ 任务分发：编排偏好路由表 → 选 worker（按项目 slot）
    │
    ▼
④ DAG 调度：拆子任务 → 节点图 → 各节点独立 worker 并行执行
    │                    （输入/产出都挂 spec）
    ▼
⑤ 质量闸门：Scorecard 自动评分（≥70 通过）→ 三道人工把关（dev→test→PM）
    │
    ▼
⑥ 交付闭环：Git release → PR → 云效流水线触发 → 通知
```

## 三、核心闭环（六步）

### Step 1 · 需求提交与评审
- 用户告诉 Hermes："我在 XX 项目空间下有一个需求"
- Hermes 自动调用「多模型融合评估」skill（my-fusion）对需求做评审
- 评审输出：需求可行性、风险点、验收标准建议

### Step 2 · 需求拆分（规范层）
- 评审通过后拆解：
  - **spec（需求）**：做什么，验收标准
  - **设计**：怎么做，技术方案
  - **契约**：输入/输出/约束的合同
- 产物形态：单一 `task.yaml`（契约载体），支持 OpenSpec 规范格式
- **必须人工确认后才能进入执行**（硬闸门，不可跳过）

### Step 3 · 任务分发
- 根据项目情况 + K3s 里的 worker 状态自动分发
- 分发依据：编排偏好路由表（task_type → provider/model）
- worker 类型：Claude Code（智谱/DeepSeek/其他模型）、Codex、OpenCode

### Step 4 · DAG 拆解与并行调度（执行层）
- 大任务拆成多个子任务，形成 DAG 工作流图
- **每个节点由一个 worker 负责**，节点输入/产出都挂 spec
- 无依赖节点**并行执行**（Multi-Agent Refactor 模式），独立 git worktree 隔离
- Hermes engine 统一调度：拓扑排序 → 分批 → 并发 → 依赖等待

### Step 5 · 质量闸门
- **Scorecard 自动评分**：6 维度（commit/diff/cost/turns/self_check/delta）
  - ≥70 自动通过 / 50-70 升级人工 / <50 自动打回
- **三道人工把关**（dev→test→PM 三级流转）：
  - dev 闸门：开发者审代码
  - test 闸门：测试人员独立验证
  - PM 闸门：业务验收

### Step 6 · 交付闭环
- Git release（制品版本记录）→ 创建 PR
- 云效流水线自动触发（CI/CD 打通）
- 通知：Hermes 消息 + 邮件
- 完成后 worker 回 idle，可接同项目下一个任务

## 四、基础设施需求

### 4.1 项目空间与 worker 关系
- **项目 ↔ worker = 1 对多**：每个项目拥有多个 worker（不同框架/模型）
- **worker ↔ 任务 = 1 对 1**：同一时刻一个 worker 只跑一个任务
- worker 完成当前任务并提交 release 后，可再接**当前项目**的其他任务
- 项目与 worker 的绑定关系由 Hermes engine 统一维护

### 4.2 Worker 热池（slot 槽位制）
- 在 K3s 里为**每个项目预制** Pod 槽位
- 选择 worker 时复用预制槽位（避免每次冷启动）
- 热池状态：idle / busy / resetting，由 Reconciler 保活

### 4.3 Pod 镜像
- 镜像内置多种开发框架：Claude Code、Codex、OpenCode
- 框架内部模型可配置：DeepSeek、GLM、Kimi K3、千问等
- 模型跑在 K3s Pod 内（或 Pod 内 CLI 调用外部模型 API）

### 4.4 启动与配置
- Pod 启动时注入 Base URL + API Key（K3s Secret 统一管理，运行时注入，不烧进镜像）
- 每个 Pod 启动时拉取**对应项目**的分支初始化
- 非 root 用户运行（Claude Code 安全要求）

### 4.5 Git 版本管理
- 全程 Git：分支隔离（worktree）、commit、push、release、PR

### 4.6 优化加速
- 构建缓存（Node/Maven 依赖缓存，PV 挂载或 pnpm store 共享）
- 共用 Node.js / Maven 环境，避免每个 Pod 重复下载依赖

### 4.7 监控与通知
- Hermes 内命令实时查看任务状态（dashboard / status / stream）
- Hook 通知机制：Hermes 主线程实时推送任务进展（完成/失败/需决策）

## 六、非功能需求

### 6.1 安全
- 凭据不落镜像、不入代码库（K3s Secret 运行时注入）
- 禁止 root 运行 agent
- 安全审计无高风险问题

### 6.2 可靠性
- API 故障自动重试（529 → 30s/60s 退避）
- Pod 崩溃 Reconciler 自动重建
- 任务断点可恢复（objective 持久化，LoopX 借鉴）

### 6.3 成本
- turns 预算 + 成本帽（默认 300 turns / $15）
- quota 控制周期任务唤醒（LoopX 借鉴）

### 6.4 性能
- 并行执行（同批无依赖子任务并发）
- 依赖缓存 + 共享构建环境

### 6.5 可扩展
- 新框架/模型：加镜像 + 路由表规则
- 新仓库：加 repos.json 条目

## 七、验收标准

1. 端到端全链路跑通：一句话需求 → 评审 → 拆解 → 分发 → 执行 → 闸门 → PR
2. 三节点以上并发运行，故障自动补位
3. 多团队数据隔离和配额功能正常
4. 监控告警体系就绪
5. 安全审计无高风险问题
6. 新用户 3 步启动：npm install → pactflow setup → pactflow start "需求"

## 九、已确认的需求决策

- 项目定名：**零脉（PactFlow）**，英文 PactFlow，全称"多智能体契约编排开发框架"
- 许可证：MIT
- 执行层：L0 本地 + L1 K3s 容器
- 契约载体：单一 task.yaml（评审后从三份 JSON 合并简化）
- 模型通道：智谱 glm-5.2（主力）、DeepSeek、OpenCode 多模型
- 质量机制：Scorecard 自动评分 + 三道人工闸门
- 对标吸收：Paseo（编排路由）、HomeRail（DAG/Scorecard/Worker 容器）、Multi-Agent Refactor（并行 worktree）、LoopX（持久化目标/quota）
